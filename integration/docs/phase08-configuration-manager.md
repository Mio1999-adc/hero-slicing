# Phase 08 — O-RAN System Configuration Manager

## Dashboard and workflow

Run `./integration/scripts/start-dashboard.sh`, then open `http://127.0.0.1:8090`. The Python standard-library server binds to loopback by default. The browser view supports editing, validation, saving/loading JSON profiles, applying a profile by launching it, monitoring child processes and logs, issuing a supported runtime control, and stopping the processes started by that dashboard instance.

The workflow is **Configure → Launch → Monitor → Control → Validate → Stop**. Each run stores logs and its CSV under `integration/build/dashboard-runs/<run-id>/`. The Requested panel displays the submitted profile. The Applied panel displays normalized settings, selected process arguments, fixed ports, identities, launch timestamp, and output directory. The server reports child process exit codes and log output; a successful process start alone does not claim E2 registration, KPM delivery, or control application.

## Verified inputs and compatibility

| GUI setting | Actual mapping | Boundary / compatibility |
|---|---|---|
| gNB count | `native-measurements --gnbs=N`; native NR helper installs N `NrGnbNetDevice`s | Native radio-only: 1–15; E2-connected: validated through 2. For >2, the dashboard explicitly normalizes to radio-only and shows a compatibility notice. IDs are `101..100+N`; at least one UE per gNB |
| UE count | `native-measurements --ues=N`; native NR helper installs N UEs and attaches them to closest gNB | 1–32 and at least as many UEs as gNBs |
| Inter-gNB spacing | `native-measurements --gnbSpacingM=M`; gNBs are placed along the x-axis | 50–5000 m |
| UE-to-assigned-gNB distance | `native-measurements --ueDistanceM=M`; UEs are placed on a ring around their round-robin assigned gNB, then native `AttachToClosestGnb` selects the serving cell | 1–500 m; when multiple gNBs are present, must be less than half the inter-gNB spacing to ensure each UE is closest to its assigned cell |
| sample interval | `--sampleMs=N`; `LenaMeasurementProvider` samples on ns-3 events | 1–10,000 ms; the dashboard offers 100 ms for responsive local charts. With the stock KPM xApp enabled, the interval must be 1,000 ms; selecting another interval disables that xApp in the UI. |
| Run mode | Dashboard passes `--duration=0` and enables native signal-aware continuous mode | Default: traffic and measurements continue in real-time until **Stop all** sends SIGINT; simulator handles the signal on its event loop, then closes providers and E2 agents |
| Finite duration | `--duration=S`; `Simulator::Stop(Seconds(S))` | Optional finite mode: 1.5–600 simulated seconds |
| RIC IPv4 | `HERO_RIC_BIND_IP` becomes the original RIC `-a` option; simulator and xApps receive the same `-a` peer address | IPv4 only; the manager starts the local RIC on the selected address |
| E2 | `--enableE2=1 --realtime=1 --ricPort=36421 --plugins=.../phase06-plugins` | Native SCTP reporting needs realtime simulation; otherwise radio-only mode uses `--enableE2=0` |
| KPM monitor xApp | Starts original `xapp_kpm_moni` with `-a <RIC IPv4>` and the inspected service-model plugin directory | It requests the supported cell DL/UL PDCP SDU metrics at 1,000 ms. Stock monitor compatibility is capped at two concurrent gNB subscriptions because its event loop aborts above two. The dashboard can chart the local native CSV catalogue for radio-only scenarios through 15 gNBs without claiming those other metrics are E2 KPM wire reports. |
| Runtime `MaxDlMcs` | Launches the original FlexRIC xApp API client with private style 32767, selected E2 gNB identity, BWP 0, and requested integer | 0–30, only while the simulator is running and private control was enabled at launch. It is a private extension, not standard E2SM-RC. |

The stock FlexRIC Near-RT RIC E2 port (36421) and xApp port (36422) are compiled constants in the inspected build (`platforms/flexric/src/ric/near_ric.c`, `platforms/flexric/src/ric/iApp/e42_iapp.c`, and `platforms/flexric/src/xApp/e42_xapp.c`). They are therefore displayed as fixed values and cannot be edited. The baseline radio profile is 3.5 GHz, 20 MHz, one BWP. The provider explicitly requires exactly one BWP because the native RRC bearer traces do not expose BWP identity; the dashboard labels this as a baseline BWP profile and does not expose unsupported bandwidth, BWP count, or scheduler attributes. Slice and live-PPO settings were added after this phase; see `slice-manager.md` and `ppo-learning.md` for their current contract.

gNB/UE counts, topology distances, sampling interval, RIC address, service connections, and run mode are startup-only in this dashboard. Radio-only runs use ns-3's unpaced simulator so they consume available CPU rather than sleeping to wall-clock time; E2-connected runs remain real-time paced for SCTP. Continuous dashboard traffic alternates between 6 ms burst intervals and 24 ms intervals with staggered UE phases to create observable changes in actual LENA measurements; finite regression scenarios retain their original constant-rate workload. Stop and relaunch to change startup settings. The only exposed runtime control remains `MaxDlMcs`; the private control xApp requires an advertised control style and checks the chosen gNB identity.

## Profiles and operation

Profiles are JSON documents in `integration/dashboard/profiles/` and can also be directed to another folder with `HERO_PROFILE_DIR`. Loading a profile preserves the current Step 1 gNB, UE, sampling, and run settings by default; enable **Also replace Step 1…** to load those fields from the profile too. This prevents a 1- or 2-gNB demo profile from silently replacing a scenario already configured in Step 1. The server rejects unknown fields, gNB counts outside 1–15, UE counts outside 1–32, out-of-range intervals/duration/control values, invalid IPv4, incompatible xApp/E2 switches, UE count below gNB count, and mismatched KPM/sample intervals. For more than two gNBs, disable the stock KPM monitor; actual LENA CSV measurements remain available to the chart panel. Each process is launched directly as an argument vector (no shell interpolation), with its own process group and captured log. Child xApp and simulation output is streamed both to the dashboard log panel and the launch terminal; per-request HTTP access logs are suppressed. **Stop all** sends an interrupt and escalates only if a child does not exit.

The KPM visualization panel reads the current run's flushed native measurement CSV incrementally and refreshes chart/log views twice per second. Its scrollable catalogue includes DL/UL PDCP SDU throughput, allocated PRB grant-sums, active/connected UE counts, MCS, DL CQI, SINR, PDCP/RLC delay, and received PDCP packet counts. Cell and per-UE scopes are available where the provider emits the field. These plots are local LENA telemetry; only the DL/UL throughput names are presently advertised and encoded as E2 KPM v3. Empty receiver windows remain missing values rather than fabricated zeros. PRB values are grant-sums per sampling window, not unique utilized PRBs or utilization percentages.

### Execution speed and visualization responsiveness

The installed ns-3 build is a debug profile (`-g`, assertions and logging enabled). A separate optimized profile is supported without replacing it; reproducible build and dashboard commands are in [integration README](../README.md#faster-radio-only-dashboard-build). Both builds use the same ns-3.42/NR-LENA source and scenario configuration. In one local comparison, the three-gNB/two-second native CTest took 20.29 s with debug libraries and 2.15 s with optimized libraries; the two-gNB counterpart took 17.16 s and 1.93 s. This is a machine-specific sample, not a runtime guarantee. Continuous optimized radio-only validation advanced 3.7 simulated seconds during a six-second wall-clock stop window and produced 37 measurement windows per gNB at 100 ms sampling.

The dashboard polls logs and chart data every 500 ms. Log-tail reads are bounded, and the chart endpoint consumes appended CSV rows incrementally instead of rescanning the whole file. Choose 100 ms sampling for fast native chart updates; the stock KPM monitor requires 1000 ms and its E2-connected simulation remains real-time paced. Radio-only simulations run unpaced and therefore use the fastest available CPU execution. The continuous dashboard workload alternates actual UDP source intervals between 6 ms bursts and 24 ms intervals with staggered UE phases. In the six-second optimized run, cell DL throughput varied across the 37 measured windows (gNB 101: 0–1.426 Mbit/s, gNB 102: 0–1.728 Mbit/s, gNB 103: 0–1.728 Mbit/s). Empty receive windows remain zero/missing according to the provider's defined measurement behavior; chart values are not synthesized.

The manager reuses an existing SCTP listener on port 36421 only when its owning process command identifies the original FlexRIC Near-RT RIC; it starts a dashboard-owned RIC only when the port is free, and refuses to launch over an unidentified listener. An adopted RIC is shown as external and is not stopped by the dashboard. E2-connected scenarios are limited to two gNBs: a 10-gNB attempt received Setup Requests for gNBs 101–107, then the remaining SCTP associations failed; original FlexRIC asserted in `assoc_rb_tree_extract` while cleaning up. A separate seven-gNB setup remained pending without Setup completion. For >2 gNBs the dashboard now automatically disables E2, KPM xApp and control in the applied configuration and launches the supported native radio-only scenario; the requested settings remain shown separately. Control actions start a short-lived control xApp and require an explicit successful response. For actual scheduler application, inspect the native simulation log for `[HERO RC PRIVATE] ... applied=1`; the generic FlexRIC control acknowledgement alone is not sufficient proof.

## Validation

Configuration rules have a focused test in `integration/tests/dashboard-config-test.py`, registered as CTest `dashboard-config-validation`. Build the native executable and control xApp first:

```sh
./integration/scripts/build-integration.sh
./integration/scripts/start-dashboard.sh
```

For a single-gNB live check, use the default profile and let the simulation complete. The native log should show gNB 101 setup and delivered DL/UL traffic; the stock KPM xApp should show a subscription and decoded reports. To test single-gNB runtime control, select an active scenario with private control enabled and use the runtime panel; the control client must resolve the one registered identity.

For multi-gNB validation, select two gNBs and at least two UEs. The verified Phase 06 end-to-end runner remains available as a direct check:

```sh
python3 -u integration/tests/run-phase06.py --duration=8 --gnbs=2 --ues-per-gnb=2
```

This runs the original RIC, stock KPM monitor, native LENA, and targeted private-control xApp and checks separate gNB KPM contexts and control routing. The full limitations for three concurrent subscriptions and the upstream Near-RT RIC unit assertion are in [Phase 07 validation](phase07-final-validation.md) and [known limitations](known-limitations.md).

The dashboard itself was exercised through its local API after opening and inspecting the rendered page. The single-gNB profile saved and loaded successfully, registered gNB 101, produced five decoded KPM records during the run, and applied `MaxDlMcs=3` to gNB 101 at simulated time 2.9 s. It delivered 2,200 DL and 1,572 UL UDP packets. The two-gNB profile registered IDs 101 and 102, produced eight decoded KPM records (four per gNB), and applied `MaxDlMcs=2` only to gNB 102 at simulated time 1.274 s; native logs recorded `applied=1 effective=2`. Its four UEs delivered 6,000 DL and 4,288 UL UDP packets. A 10-gNB/10-UE radio-only native run completed with all ten IDs 101–110, nonzero DL/UL SDU bytes and PRB grant-sums per gNB, and 1,000 DL/800 UL delivered UDP packets. The dashboard mapper returned 600 CSV chart points across those ten gNB IDs; peak cell-window DL/UL PDCP SDU throughput was 0.864/0.3408 Mbit/s. The live UI displayed DL/UL charts from an actual two-gNB dashboard-launched CSV run. A 15-gNB profile validated in radio-only mode, but a 15-gNB traffic run did not finish within a 120-second execution limit; it had emitted seven 100-ms measurement windows when the test limit expired. E2 remains restricted to two gNBs due the observed original-RIC concurrency and cleanup failures above. The original process arguments and log snapshots are retained under `integration/build/dashboard-runs/` for this workspace.
